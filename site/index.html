Layer analysis

What each layer actually proves.

The goal is not to defend a pyramid shape. It is to make the protected risk explicit and then ask whether that risk can be covered more cheaply without losing detection.

01

Unit

Business rules, calculations, validation, and boundary values.

Strong at
Fast feedback and precise rule failures.
Does not prove
HTTP authorization, composition, DOM execution, or network wiring.
Observed trade-off
Fastest runtime, but unit-only detected only 6/12 realistic mutants in the lattice.
02

Integration

HTTP contract, authorization, status codes, and error payloads.

Strong at
Seams where domain behavior meets the public API.
Does not prove
Real browser execution or complete UI composition.
Observed trade-off
Protects an authorization defect that no other complete layer killed in the measured panel.
03

System E2E

Composed application flow through the public HTTP boundary.

Strong at
Cross-component behavior and externally visible system flow.
Does not prove
That a real browser executes client code correctly.
Observed trade-off
Broader confidence than isolated tests, while remaining much cheaper than the browser run in the current runtime benchmark.
04

Browser E2E

Real DOM execution, client-side JavaScript, and network wiring.

Strong at
Browser-visible composition and the final client/network seam.
Does not prove
Every lower-level business rule efficiently.
Observed trade-off
Most expensive measured layer; retained because its protected risk is different, not because broad E2E coverage is inherently better.

Methodology

Evidence should be reproducible.

Every number needs a protocol and an interpretation boundary. Otherwise a benchmark becomes decoration.

1

Run comparable scopes

Each layer is executed independently using the same repository commit and runner context.

2

Warm before measuring

The default runtime protocol uses one warmup and five measured executions, then reports median and p95.

3

Keep raw evidence

TAP logs, JSON, Markdown, test-file SHA-256 hashes, and Allure output are preserved as traceability evidence.

4

Separate cost from effectiveness

Runtime answers “how expensive?” Mutation/lattice evidence answers “what defects are lost if this layer disappears?”

5

Use benign controls

Expected-surviving refactors protect the experiment from rewarding brittle tests that fail on harmless changes.

6

Do not overgeneralize

The conclusion applies to this repository, bucket, mutant panel, runner, data, and protocol. A different product needs a new measurement.

Quality-first pruning rule

Before removing an expensive layer, identify the realistic defect it uniquely guards, add a cheaper independent test that kills the same defect, rerun the full protocol, and remove the expensive check only if ceiling detection is preserved.
